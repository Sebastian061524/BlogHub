# BlogHub 数据库设计草案

> 对应 `requirements.md`，用于 Day 1 设计审查，尚未生成或执行建表 SQL。
> 保留你选择的四表结构、自增整数主键、外键和分类名称唯一约束。
> 表名、密码字段、时间类型、容量调整、索引及删除实现由导师补充为建议方案，后续可讨论调整。

## 1. 通用约定

- 建议表名统一使用 `blog_` 前缀，字段统一采用小写字母和下划线命名。
- Java 实体、DTO／VO 字段统一使用小驼峰命名（camelCase）；JSON 请求和响应字段、查询参数及路径参数占位符与对应 Java 字段保持同名，详见 api.md。
- 数据库列名继续使用下划线，通过 MyBatis 的结果映射或驼峰映射转换为 Java 字段；这与 Jackson 处理 JSON 是两个独立环节，接口不使用全局 SNAKE_CASE 命名策略。
- 建议使用 MySQL InnoDB 引擎、`utf8mb4` 字符集。
- 主键沿用 `INT` 自增；所有引用该主键的外键保持相同类型及符号属性。
- 下文所有字段均不允许 `NULL`；主键由数据库自增生成。
- “无默认值”表示写入时必须提供，不能依赖空字符串、0 等值代替必填数据。
- 字符串长度为存储容量，非空、非纯空白、最小长度等规则仍需业务层校验。
- 用户名按需求去除首尾空白后使用并保留大小写，注册、登录查询和唯一性判断均区分大小写，不得统一转成小写；用户名列应采用区分大小写的比较规则，具体排序规则在编写建表 SQL 时落实。

常见字段对应关系：

| 数据库列名 | Java 字段／对应接口属性 |
| --- | --- |
| user_name | userName |
| user_id | userId |
| category_name | categoryName |
| category_id | categoryId |
| article_id | articleId |
| create_time | createTime |
| update_time | updateTime |

数据库中的 `password_hash` 对应实体字段 `passwordHash`，不接受客户端指定，也不在响应中返回。注册和登录 DTO 使用 `password` 接收原始密码。实体主键 `id` 对外组织成 articleId、categoryId、commentId 等标识时，由响应对象明确映射，不是自动给数据库列添加前缀。

## 2. 用户表：`blog_user`

| 字段 | 类型 | 可空 | 默认值 | 约束 | 用途 |
| --- | --- | --- | --- | --- | --- |
| id | INT | 否 | 自增生成 | 主键 | 用户唯一标识 |
| user_name | VARCHAR(20) | 否 | 无 | 唯一 | 登录用户名，业务长度为 3–20 个字符 |
| password_hash | VARCHAR(255) | 否 | 无 | 不得存明文 | 保存密码哈希的完整编码结果 |

设计说明：

- 用户名容量从 50 调整为 20，与当前需求上限一致；唯一约束应阻止完全相同的用户名重复写入，同时允许 Alice 和 alice 分别存在。
- `password` 建议改名为 `password_hash`，明确数据库保存的不是原始密码。
- 建议用 255 个字符预留哈希编码存储空间；它与用户输入密码的 6–64 个字符限制是两回事。
- 密码输入仅允许英文字母、数字和英文半角标点（ASCII U+0021–U+007E），拒绝所有空白和范围外字符，不自动删除字符；该规则在注册和登录时校验，不改变 password_hash 字段的存储用途。
- 密码哈希算法及参数在认证开发时选择，并核对输出容量；接口和日志均不得暴露该字段。
- 注册前查询用户名只能改善提示，最终仍需依赖数据库唯一约束处理重复写入。
- 注册和登录 DTO 保留输入校验注解，setter 仅负责赋值。Service 在查询数据库前调用共用的 UserInputValidator：先去除用户名首尾空白（null 保持为 null，保留大小写），再通过 jakarta.validation.Validator 执行 DTO 校验；密码保持原样，校验失败转为 HTTP 400 的业务异常。
- 注册 Controller 使用 @RequestBody 接收 JSON，将规范化和校验交给 Service，不在该参数上提前执行 @Valid；保留的 /debug/validate-register 接口复用同一个 Service 层输入校验组件，因此 HTTP 请求与直接调用 Service 的输入规则一致。

## 3. 文章表：`blog_article`

| 字段 | 类型 | 可空 | 默认值 | 约束 | 用途 |
| --- | --- | --- | --- | --- | --- |
| id | INT | 否 | 自增生成 | 主键 | 文章唯一标识 |
| user_id | INT | 否 | 无 | 外键，引用 blog_user.id | 作者，来自当前登录身份 |
| title | VARCHAR(50) | 否 | 无 | 业务层校验非纯空白 | 文章标题 |
| body | VARCHAR(1000) | 否 | 无 | 业务层校验非纯空白 | 文章正文 |
| category_id | INT | 否 | 无 | 外键，引用 blog_category.id | 所属分类 |
| create_time | DATETIME | 否 | 数据库当前时间 | 创建后不修改 | 发布时间 |
| update_time | DATETIME | 否 | 数据库当前时间 | 修改文章时由业务层更新 | 最近修改时间 |

设计说明：

- 标题和正文容量分别从 100、10000 调整为 50、1000，与当前 MVP 的需求上限一致。
- 原草案的 `DATE` 只能保存日期，改为 `DATETIME`，以记录一天内的发布时间和修改时间。
- 同一发布时间的文章按 id 倒序排列，避免同一时间的数据没有明确顺序。
- 新建文章时两项时间应一致；修改标题、正文或分类时，只更新修改时间，不改变作者及发布时间。
- 当前正文上限为 1000 个字符，使用 `VARCHAR(1000)` 足够；以后扩大正文范围时再评估 `TEXT`，本周不提前扩展。

## 4. 分类表：`blog_category`

| 字段 | 类型 | 可空 | 默认值 | 约束 | 用途 |
| --- | --- | --- | --- | --- | --- |
| id | INT | 否 | 自增生成 | 主键 | 分类唯一标识 |
| category_name | VARCHAR(20) | 否 | 无 | 唯一 | 分类名称 |

设计说明：分类由初始化数据提供，不开放新增、修改和删除接口；保留你选择的名称唯一约束。

## 5. 评论表：`blog_comment`

| 字段 | 类型 | 可空 | 默认值 | 约束 | 用途 |
| --- | --- | --- | --- | --- | --- |
| id | INT | 否 | 自增生成 | 主键 | 评论唯一标识 |
| article_id | INT | 否 | 无 | 外键，引用 blog_article.id | 所属文章 |
| user_id | INT | 否 | 无 | 外键，引用 blog_user.id | 评论者，来自当前登录身份 |
| text | VARCHAR(500) | 否 | 无 | 业务层校验非纯空白 | 评论内容 |
| create_time | DATETIME | 否 | 数据库当前时间 | 创建后不修改 | 评论发布时间 |

设计说明：

- 保留你补充的评论者关联，并增加评论发布时间，支持返回评论者信息和按时间排序。
- 内容容量从 5000 调整为 500，与需求上限一致。
- 本周只做单层评论，无需父评论字段。

## 6. 表之间的关系与外键

| 父表 → 子表 | 关系 | 子表关联字段 | 父记录删除／主键更新规则 |
| --- | --- | --- | --- |
| blog_user → blog_article | 一个用户可发布多篇文章，每篇文章只有一个作者 | blog_article.user_id | RESTRICT |
| blog_category → blog_article | 一个分类可包含多篇文章，每篇文章只有一个分类 | blog_article.category_id | RESTRICT |
| blog_article → blog_comment | 一篇文章可有多条评论，每条评论只属于一篇文章 | blog_comment.article_id | RESTRICT |
| blog_user → blog_comment | 一个用户可发布多条评论，每条评论只有一个评论者 | blog_comment.user_id | RESTRICT |

建议本周实际创建这些数据库外键，防止产生无效关联。`RESTRICT` 表示存在子记录时，不能直接删除父记录或修改其主键。

外键负责引用完整性，不能代替登录认证和作者权限校验；存在合法的 user_id 不代表当前调用者有权修改文章。

## 7. 索引建议及对应查询

| 表 | 索引字段（按顺序） | 类型 | 对应用途 |
| --- | --- | --- | --- |
| 四张表 | id | 主键索引 | 按唯一标识查询和关联 |
| blog_user | user_name | 唯一索引 | 登录查找、保证用户名唯一 |
| blog_category | category_name | 唯一索引 | 保证分类名称唯一 |
| blog_article | create_time, id | 普通联合索引 | 全部文章按发布时间及 id 倒序分页 |
| blog_article | category_id, create_time, id | 普通联合索引 | 按分类筛选后按时间及 id 倒序分页 |
| blog_article | user_id | 普通索引 | 支持作者外键约束 |
| blog_comment | article_id, create_time, id | 普通联合索引 | 查询某篇文章的评论并按时间及 id 正序排列，也支持按文章删除评论 |
| blog_comment | user_id | 普通索引 | 支持评论者外键约束 |

说明：

- 联合索引按筛选与排序需求设计，后续用实际 SQL 的执行计划验证，不提前声称已优化性能。
- 上述以 category_id、article_id 开头的索引也可支持对应外键，无需再机械添加相同前导字段的单列索引。
- MySQL 可能自动创建外键所需的索引；生成建表 SQL 时应核对实际定义，避免重复创建。
- 本周没有标题搜索功能，不添加标题搜索索引。

## 8. 文章删除方案

建议使用物理删除，由业务层在同一个数据库事务内完成，不配置数据库级联删除：

1. 验证当前用户已经登录。
2. 查询文章是否存在，并检查当前用户是否为作者。
3. 删除该文章所属的全部评论。
4. 删除文章，并确认删除结果符合预期。
5. 全部成功才提交；任一步失败则回滚整次删除。

选择理由：删除顺序满足外键约束，同时便于在本项目中理解事务如何保证多表操作的一致性。

- 没有评论的文章也可以删除；删除评论影响 0 行属于正常情况。
- 文章不存在时返回资源不存在，越权时拒绝操作，均不得先删除评论。
- 外键阻止残留评论引用不存在的文章；若并发写入导致约束冲突，必须让删除失败并回滚，不得忽略异常。
- 用户和分类本周不提供删除功能，不引入额外的级联删除规则。
